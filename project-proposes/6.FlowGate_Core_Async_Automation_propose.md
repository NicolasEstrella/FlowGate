# Proposal 6 - FlowGate Core Async Automation

## Repositorio alvo

FlowGate.Core

## Objetivo

Adicionar a camada assincrona do FlowGate para notificacoes, geracao de documentos PDF, monitoramento de SLA e escalonamento automatico. Os workers rodam dentro do mesmo processo da API como Hosted Services. A publicacao de eventos e garantida pelo padrao Transactional Outbox do MassTransit com EF Core.

## Decisoes Arquiteturais (tomadas em sessao de explore em 17/05/2026)

| Decisao | Escolha | Racional |
|---|---|---|
| Onde rodam os workers | Hosted Services no mesmo processo da API | Simplicidade, deploy unico, escala suficiente para uso local |
| Garantia de entrega de eventos | MassTransit Transactional Outbox + EF Core | Evita inconsistencia entre DB commit e publicacao no broker |
| Geracao de PDF | QuestPDF | Sem dependencias nativas, API fluente em C#, licenca gratuita para uso pessoal |
| Monitoramento de SLA | Polling via BackgroundService | Query periodica em ApprovalSteps com DueAtUtc < NOW(), latencia aceitavel para o contexto |
| Armazenamento de documentos | Volume Docker local montado em /app/documents | Aplicacao roda apenas localmente; MinIO removido da stack (ver Proposal 6a) |

## Escopo

### MassTransit + RabbitMQ

- Adicionar pacotes `MassTransit` e `MassTransit.RabbitMQ` ao projeto.
- Configurar MassTransit com transporte RabbitMQ apontando para o broker local do docker-compose.
- Habilitar **Transactional Outbox** com EF Core (`MassTransit.EntityFrameworkCore`) para garantir que eventos so sejam publicados apos o commit da transacao principal.
- Registrar consumidores no container de DI.

### Contratos de Eventos (Domain Events)

Definir os seguintes contratos em `Application/Contracts/Events/`:

- `RequestCreatedEvent` — publicado ao criar uma instancia de workflow
- `RequestSubmittedEvent` — publicado ao submeter uma solicitacao
- `ApprovedEvent` — publicado quando uma etapa de aprovacao e concluida com aprovacao
- `RejectedEvent` — publicado quando uma etapa e rejeitada
- `AdjustmentRequestedEvent` — publicado quando um aprovador solicita revisao
- `RequestCompletedEvent` — publicado quando todas as etapas sao concluidas
- `EscalationTriggeredEvent` — publicado pelo SLA monitor ao detectar deadline expirado

Todos os eventos devem conter: `WorkflowInstanceId`, `CorrelationId`, `OccurredAtUtc`.

### Hosted Services (Workers dentro do processo)

Implementar como `BackgroundService` em `Infrastructure/Workers/`:

**NotificationWorker**
- Consome `RequestSubmittedEvent`, `ApprovedEvent`, `RejectedEvent`, `RequestCompletedEvent`, `EscalationTriggeredEvent`.
- Implementacao inicial: log estruturado simulando o envio (provedor real fora de escopo).
- Interface `INotificationService` para facilitar troca futura por email/webhook real.

**DocumentWorker**
- Consome `ApprovedEvent` (etapa final) e `RequestCompletedEvent`.
- Gera PDF do comprovante de aprovacao usando **QuestPDF**.
- Salva o arquivo em `/app/documents/{instanceId}/{timestamp}.pdf` (volume local Docker).
- Registra o path do arquivo no banco (campo `DocumentPath` na entidade, a criar).
- Interface `IDocumentStorageService` para isolar o acesso ao filesystem.

**SlaMonitorWorker**
- `BackgroundService` com timer periodico (intervalo configuravel via `appsettings`, default: 5 minutos).
- A cada ciclo, consulta `ApprovalSteps WHERE Status = InProgress AND DueAtUtc < NOW()`.
- Para cada step expirado: publica `EscalationTriggeredEvent` e registra auditoria.
- Idempotente: nao republica evento se escalonamento ja foi registrado.

### Politicas de Retry e Idempotencia

- Configurar retry com backoff exponencial no MassTransit para todos os consumidores.
- Definir fila de erro (dead-letter) para mensagens que esgotam retries.
- Consumidores verificam se o evento ja foi processado antes de agir (via campo na entidade ou tabela de mensagens processadas do Outbox).

### Auditoria

- Cada evento consumido com sucesso gera um `AuditLog` associado ao `WorkflowInstanceId`.
- Campo `CorrelationId` propagado em todos os logs e auditoria para rastreabilidade.

### Configuracao

Adicionar em `appsettings.json`:
```json
{
  "RabbitMq": {
    "Host": "localhost",
    "Port": 5672,
    "Username": "guest",
    "Password": "guest"
  },
  "Storage": {
    "DocumentsPath": "/app/documents"
  },
  "SlaMonitor": {
    "PollingIntervalMinutes": 5
  }
}
```

## Entregas esperadas

- Publicacao e consumo de eventos funcionando localmente via RabbitMQ.
- Pipeline assincrono: solicitacao criada → evento → notificacao (log).
- Pipeline assincrono: aprovacao concluida → evento → PDF gerado → salvo em volume local.
- Escalonamento automatico por expiracao de DueAtUtc com auditoria.
- Outbox garantindo consistencia entre estado do banco e publicacao de evento.
- Retries e dead-letter configurados para todos os consumidores.

## Criterios de aceite

- A criacao de uma solicitacao publica `RequestCreatedEvent` observavel no broker.
- Uma aprovacao final concluida gera um PDF salvo em `/app/documents/`.
- O vencimento de um step com `DueAtUtc` expirado aciona escalonamento auditavel.
- Falhas transitivas em consumidores possuem retries com backoff definido.
- O Outbox garante que nenhum evento e perdido se o broker estiver temporariamente indisponivel.
- O modelo assincrono nao quebra a consistencia do estado principal do workflow.
- Cobertura de testes unitarios para workers e consumidores (mock do bus MassTransit).

## Prompt sugerido

Adicionar em `FlowGate.Core` a camada assincrona com MassTransit + RabbitMQ + Transactional Outbox (EF Core), eventos de dominio (`RequestCreatedEvent`, `ApprovedEvent`, `RejectedEvent`, `RequestCompletedEvent`, `EscalationTriggeredEvent`), tres Hosted Services no mesmo processo (NotificationWorker, DocumentWorker com QuestPDF, SlaMonitorWorker com polling), armazenamento de PDFs em volume local Docker (`/app/documents`) e politicas de retry/idempotencia. O objetivo e refletir a arquitetura event-driven dos docs, garantir consistencia via Outbox e suportar notificacao, geracao documental e escalonamento automatico sem acoplar ao fluxo sincrono da API.
